>It’s technically not pass by reference. Java always passes by value and not reference (unlike other languages) but it makes a copy of whatever the variable is pointing to in the stack memory. Since this is a reference which points to a location in the heap memory for objects, the copied variable will hold a copy of the same reference which points to the same object in the heap. 
>
>This is why you can reassign the variable in a method (for example, writing array = new int[]{} in this case) it doesn’t change the outside variable. If it was truly pass by reference, reassigning the reference would make the whole reference point to a new object in the heap which would change what the outside variable holds when reassigning

<mark class="hltr-red">## Interfaces</mark>

Contract 
	If a class decides to implement an interface then it has to adhere to contract and implement what is inside the interface as-is 
Abstract classes 
	Attributes and set of methods
	At least one method without any limitation 
	We can have a reference variable of type abstract class but not an object 
		If there is an abstract method inside an abstract and a subclass uses this then it needs to implement the method as is otherwise the program will not compile 

General contract-based design 
	**Define an interface** -> Define contract for exposed behaviour 
	**Define an abstract class** -> Implement interface and provide some implementation of the methods inside it (These methods should be common between all subclasses that will extend this abstract class)
	**Specialise and instantiate** -> Concrete implementation that will take care of everything else. Objects are not defined for abstract class, only for subclass that define everything inside. 

	You shouldn't describe how a method should be implemented in the abstract classes only in the concrete classes

	Interfaces are always a [good practice]

	Decouple interface from implementation 
	API can evolve without disruption to the existing users of the API
	Defer decision

	**Why are interface ideal for defining mixins?**
	Loosely speaking, a mixin is a type that a class can implement in addition to its “primary type,” to declare that it provides some optional behavior. 
	
	
For example, Comparable is a mixin interface that allows a class to declare that its instances are ordered with respect to other mutually comparable objects. Such an interface is called a mixin because it allows the optional functionality to be “mixed in” to the type’s primary functionality. Abstract classes can’t be used to define mixins for the same reason that they can’t be retrofitted onto existing classes: a class cannot have more than one parent, and there is no reasonable place in the class hierarchy to insert a mixin.
